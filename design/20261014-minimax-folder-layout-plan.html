Folder-Native Constraints

分组 = Chrome 顶层文件夹

这意味着分组名和数量都不是设计能控制的变量。排版的任务只剩一个：接住任意长度、任意数量、任意语言的文件夹名。

Constraint C · 待确认

Chrome 文件夹可以嵌套，当前页面只渲染了两层

这个需要你确认一下

Chrome 书签是树状结构：顶层文件夹 → 子文件夹 → 书签。如果你的文件夹里有子文件夹（比如 AI / 图像生成 / Midjourney），那当前页面把内容平铺成一层，嵌套层里的书签要么被合并计数、要么根本没显示。

543 这个数字是否已经包含了所有层级的书签？如果没有，那问题就不是排版，而是有内容没被渲染出来——这是纯排版优化修不了的。

如果确实存在子文件夹，排版上的解法是钻取式面包屑：左栏只在顶层显示文件夹，进入后子文件夹以列表分组的形式出现，每组一行小标题。数据结构完全不动，只是把已有的第三层显示出来。

Rules

落到排版上的六条硬规则

全部只涉及栅格、字号、间距与状态，不触碰文件夹结构与书签数据。

左栏保序严格按 Chrome 里的文件夹顺序展示，任何情况下不重排
名称单行行高恒定 32px，超长省略 + 悬停全称；不做折行
计数右对齐等宽字体、固定 32px 宽列，长短名称不推挤数字
小组内联预览计数 ≤ 5 的文件夹悬停浮出内容，把"要不要点"变成零风险
空组原地置灰计数 0 只降透明度，不移动位置、不折叠隐藏
左栏独立滚动切换分组时自动滚入可见区；超 40 个文件夹时顶部加筛选框（筛选 ≠ 排序）

这些是明确不做的

按数量重排左栏 · 按频次置顶文件夹 · 给文件夹自动改名或打标签 · 折叠左栏做全屏模式 · 在左栏做多层树形展开。

前四条都会破坏你已经建立的顺序记忆，第五条会让 21 个文件夹彻底无法扫视。

文件夹名与计数取自你提供的页面截图；「待整理 2026-11」「公司 0」「精选网站 0」为演示溢出与空组状态而添加的示例项。子文件夹一节为条件预案，需先确认你的书签是否存在嵌套层级。
